# Build Tools Roadmap (DRAFT)

Status: **draft for discussion.** Written November 2026.

What we would add to `utilities/build-tools` so it can generate the new CSP
course, starting with the smallest useful core:

1. basic templates,
2. page generation,
3. a very lightweight file watcher.

Context and the things this doc takes as given (content layout, manifest, URL
scheme) are in the [CSP migration plan](./csp-migration-plan.md).

## 1. What exists today

`utilities/build-tools` is about 1,600 lines of Ruby.

| File | Does | Reusable for page generation? |
| --- | --- | --- |
| `topic.rb` (`BJCTopic`) | Parses `.topic` files, lists a unit's pages in order | Yes — becomes the importer that converts `.topic` to a manifest |
| `course.rb` (`BJCCourse`) | Finds a course's topic files by scraping `course/*.html` | Replaced by the manifest |
| `vocab.rb`, `selfcheck.rb`, `atwork.rb` | Scrape pages with Nokogiri, emit summary pages | Yes — the extraction logic; the output side changes |
| `index.rb` | Builds the alphabetical vocab index | Yes |
| `main.rb`, `rebuild-all.rb` | Drive one course/language at a time | Replaced by the new entry point |
| `bjc_helpers.rb` | Path/URL mapping, i18n setup | Partly |
| `bjc_translations.yml` | UI strings (en, es, de) | Yes |

Dependencies already in the Gemfile: `nokogiri`, `i18n`, `activesupport`,
`htmlbeautifier`, `twitter_cldr`. Tests are RSpec, in `utilities/specs`.

### Things in the current code that block reuse

These need fixing first (milestone M0), because a generator and a watcher run
many builds in one process:

- **Global working directory.** `Main` and the generators call `Dir.chdir` and
  then read files by bare name.
- **Global state.** `BJCHelpers.current_topic` is a module-level variable.
- **Root must be named `bjc-r`.** `Main` and `BJCCourse` raise otherwise, and
  URL mapping swaps a path prefix that assumes it.
- **Output goes into the source tree**, including rewriting `.topic` files.
- **HTML is built by string concatenation** (`Index#html_document`,
  `write_html_head`, and similar in each generator).
- **Links carry `?topic=…&course=…`** (`generate_url_suffix`).

## 2. Target shape

```
utilities/build-tools/
  bin/bjc                  # entry point: build | watch | check | port
  lib/
    site.rb                # one build: config, manifests, output dir
    manifest.rb            # course.yml → Course / Unit / Lab / Page objects
    page.rb                # one source page: metadata + body
    renderer.rb            # ERB layouts and partials
    transforms/            # Nokogiri passes over a page body
    collectors/            # vocab, self-check, @Work (from today's generators)
    writer.rb              # writes _site/, only files that changed
    watcher.rb             # polling watcher
    legacy/topic.rb        # today's BJCTopic, used by `port`
site/
  layouts/                 # page.html.erb, unit.html.erb, course.html.erb, …
  partials/                # navbar, footer, prev-next, translations menu
```

Commands:

| Command | Does |
| --- | --- |
| `bjc build` | Full build into `_site/` |
| `bjc build --only csp --lang es` | Limit, as `rebuild-all.rb` does today |
| `bjc watch` | Build, then rebuild on change |
| `bjc check` | Build, then report broken links, orphans, missing translations |
| `bjc port OLD NEW` | Port a legacy page (migration plan, section 10) |

`_site/` is gitignored. The existing summary pages for **legacy** courses keep
being generated by the current `rebuild-all.rb`, untouched, until those
courses migrate.

## 3. Core part 1 — templates

**Engine: ERB.** It is in Ruby's standard library, so it adds no dependency,
and templates are written by developers, not authors. Liquid is the
alternative if we ever want authors to edit templates safely; nothing here
prevents switching later.

Layouts for launch:

| Layout | Replaces |
| --- | --- |
| `base.html.erb` | `loader.js` — `<head>`, CSS, scripts, analytics |
| `page.html.erb` | `curriculum.js` — title, navbar, prev/next, progress, footer |
| `unit.html.erb` | `topic.js` — the unit's table of contents |
| `course.html.erb` | `course/*.html` + `course.js` |
| `summary.html.erb` | The string-built HTML in `index.rb`, `vocab.rb`, `selfcheck.rb` |
| `redirect.html.erb` | — (new) |

What a layout receives:

```ruby
# Available inside page.html.erb
page.title        # "Programming a Game"
page.body         # transformed HTML
page.lang         # "en"
page.url          # "/bjc-r/courses/csp/intro/click-alonzo/programming-a-game.html"
page.prev, page.next
page.translations # { "es" => "/bjc-r/…/programming-a-game.es.html" }
lab, unit, course # the page's place in the manifest
t("next")         # UI string in the page's language
url("/img/x.png") # prefix-aware URL helper
```

Rules that keep templates small:

- No logic beyond loops and conditionals. Anything else is a method on the
  model.
- All URLs go through `url(...)`, so the `/bjc-r` prefix lives in one place.
- All UI text goes through `t(...)`.

## 4. Core part 2 — page generation

### Source page format

Recommended: **source pages stay complete HTML documents**, as they are now.

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Programming a Game</title>
  </head>
  <body>
    <div class="learn">…</div>
  </body>
</html>
```

- The build takes the title from `<title>`, the language from `<html lang>`
  (or the `.es.` suffix), optional metadata from `<meta name="bjc:…">`, and the
  content from `<body>`.
- Files open correctly in any HTML editor, and porting an old page is mostly
  deleting the `loader.js` line.
- Position (unit, lab, page number) comes from the manifest, not the page.
  Titles like "Unit 1 Lab 1 … Page 1" are no longer written by hand.

The alternative — a body fragment with YAML front matter — is slightly nicer
for metadata but no longer a valid HTML file. This is open question O4 in the
migration plan.

### Pipeline

```
load manifests ─▶ resolve pages ─▶ parse ─▶ transform ─▶ collect ─▶ render ─▶ write
```

1. **Load manifests.** `course.yml` → `Course`, `Unit`, `Lab`, `Page` objects.
   Each page knows its neighbours and its output URL.
2. **Resolve pages.** For each language, find `page.<lang>.html` or apply the
   course's fallback rule. Missing files are errors, with the manifest line.
3. **Parse.** Nokogiri HTML5, once per source file. The parsed result is
   cached by path and mtime, which is what makes the watcher cheap.
4. **Transform.** Ordered Nokogiri passes over the body. For launch:
   - content anchors (`vocab-1`, …) — removes the need for `llab` and Ruby to
     agree on numbering;
   - internal link and image URL resolution (relative → final URL);
   - Snap! run links (`a.run`);
   - quiz markup expansion;
   - `ifTime` / `takeItFurther` → `<details>`;
   - removal of developer-only content (`todo`, `comment`, …) in production
     builds.
5. **Collect.** Vocab, self-check, exam-reference and "@ Work" collectors read
   the transformed page. This is today's extraction code, taking a parsed page
   as an argument instead of reading the current directory.
6. **Render.** Page → `page.html.erb` → `base.html.erb`. Then unit pages,
   course pages, summary pages from the collectors, and redirect stubs.
7. **Write.** Into `_site/bjc-r/…`. A file is only written if its content
   changed, so timestamps stay meaningful for deploys and for the watcher.

Summary pages become ordinary generated pages listed in the unit navigation.
The build no longer edits manifests or commits output, and the "Summaries are
up to date" CI job goes away for built courses.

### Legacy content is not copied during development

`img/` and `sparks/` are over 1.2 GB. Copying them on every build would defeat
the purpose of a fast watcher.

- **Development:** `utilities/server.py` looks in `_site/` first and falls back
  to the repository root. Legacy pages and assets are served from where they
  already are. This is a small change to `BJCRequestHandler`.
- **Deploy:** CI assembles the full tree once (legacy directories + `_site/`).

### Errors

A build that fails writes nothing — the same guarantee `Main` gives today with
`@pending_writes`. Errors name the source file and, where possible, the line:

```
content/courses/csp/course.yml: unit "intro", lab "click-alonzo":
  page "keeping-scor" not found (did you mean "keeping-score"?)
```

In watch mode, an error is printed and the previous output stays in place.

## 5. Core part 3 — a very lightweight file watcher

**Approach: poll modification times.** No new dependency, and it behaves the
same on macOS, Linux, Windows and WSL — the platforms `./run-server` supports.
The `listen` gem is the upgrade path if polling ever proves too slow; with a
few hundred source files it should not.

```ruby
# Sketch, not final code
class Watcher
  GLOBS = %w[content/**/* site/**/*].freeze

  def run(interval: 0.5)
    seen = snapshot
    loop do
      sleep interval
      now = snapshot
      changed = (now.keys | seen.keys).reject { |path| now[path] == seen[path] }
      seen = now
      rebuild(changed) unless changed.empty?
    end
  end

  def snapshot
    Dir.glob(GLOBS).select { |f| File.file?(f) }.to_h { |f| [f, File.mtime(f)] }
  end
end
```

What gets rebuilt:

| Changed file | Rebuild |
| --- | --- |
| A page | That page in every edition and language that uses it, plus its unit's summary pages |
| A manifest | Everything in that course (navigation changes on every page) |
| A layout or partial | Everything |
| CSS, JS, images under `content/` or `site/` | Copy the file |

The first version can simply do a **full rebuild on every change** — parsed
pages are cached, so only the changed file is re-parsed — and move to the table
above only if a full rebuild is noticeably slow. That needs measuring; the
build does not exist yet.

Deliberately left out of the first version:

- **Live reload.** The dev server already sends no-cache headers for `.html`,
  `.css` and `.js`, so a manual refresh shows the new build.
- **Watching legacy directories.** Nothing is generated from them.

### One command for authors

`./run-server` stays the single supported command. It starts the Python server
as it does now and launches `bjc watch` as a child process, stopping both on
Control-C. If Ruby is not installed it says so and serves legacy content only.

The watcher lives in Ruby rather than in `server.py` so that manifests and
parsed pages stay in memory between rebuilds, instead of paying Ruby and
Bundler start-up on every save.

## 6. Milestones

| | Milestone | Done when |
| --- | --- | --- |
| M0 | **Refactor for reuse.** Remove `Dir.chdir` and global state; make the root path a parameter; separate extraction from output. | Existing specs pass; `rebuild-all.rb` output is byte-identical |
| M1 | **Templates + one page.** ERB renderer, `base` and `page` layouts, body extraction, write to `_site/`. | One ported page renders at its new URL with no `llab` |
| M2 | **Manifest + navigation.** Models, prev/next, `unit` and `course` layouts, language resolution. | One unit is browsable in English and Spanish |
| M3 | **Watcher + `./run-server`.** Polling watcher, server overlay of `_site/`. | Saving a page shows the change on refresh |
| M4 | **Transforms + collectors.** Anchors, links, Snap! links, quizzes; vocab, self-check, "@ Work" pages. | Unit review pages match today's in content |
| M5 | **Check + deploy.** Link/orphan/translation reports, redirect stubs, CI build and publish. | A pull request fails on a broken link; `main` deploys |

M1–M3 are the "basic templates, page generation and lightweight watcher" core.

### After launch, in rough priority order

- `bjc port` and the `.topic` → manifest converter (may be needed earlier for
  authors — see migration plan, section 10)
- Editions (second manifest → `csp-2028/`)
- Directive-style shortcuts for verbose structures, starting with quizzes
- Build-time KaTeX and syntax highlighting
- Pandoc: as an input format for selected file extensions, and as an output
  step for docx/PDF (formalising the manual recipe in `utilities/README.md`)
- Markdown pages
- Search index
- Live reload

## 7. Testing

- **Unit specs** for manifest loading, page resolution, each transform and
  each collector — fast, no browser, alongside `build_tools_spec.rb`.
- **A fixture course** under `utilities/specs/fixtures/` with a handful of
  pages; the spec builds it and compares against checked-in expected output.
- **`bjc check`** runs in CI on the real content.
- **Accessibility specs** point at `_site/` for built courses.

## 8. What we take on by building this ourselves

Written down so the choice against Eleventy (migration plan, O1) is made with
the costs visible:

- We own the template conventions, routing, watcher and incremental logic, and
  their bugs.
- There is no plugin ecosystem; every feature in "After launch" is ours to
  write.
- Documentation for the next maintainer is whatever we write.

What we get in return: one language, no new toolchain for authors, direct reuse
of the topic parser, summary generators, translations and specs, and a
generator that does exactly what this curriculum needs and nothing else.

A reasonable checkpoint: after M3, compare the time spent against the spike of
the same unit in Eleventy, and decide then.
